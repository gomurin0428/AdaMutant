# AdaMutant

[English](README.md) | **日本語**

Ada / SPARK 向けのミューテーションテストツールです。.NET の [Stryker.NET](https://stryker-mutator.io/docs/stryker-net/introduction/) と同じ考え方で、ソースに小さな変更（ミュータント）を自動で入れ、テストと GNATprove の証明がその変更を検出できるかを調べ、**ミューテーションスコア**を出します。

- Ada 2022 までの字句解析器を内蔵（libadalang などの追加依存なし）
- **テストで検出できなかったミュータントを GNATprove の証明にかける**（SPARK 向け）。証明だけが検出したミュータントは、テストの穴の候補として一覧に出す
- **ミュータントをまとめて 1 回でビルド**し、テストはどのミュータントを有効にするかを切り替えながら実行する（ミュータント・スキーマ）。ミュータントごとにビルドし直さないので速い
- **テストが実行しないコードのミュータントは、テストを飛ばして証明にかける**。変更前のテストがどの場所を実行したかを記録して決める
- **テストごとの結果**。テストコマンドを名前付きで複数書くと、どのテストがどのミュータントを実行し、検出したかをレポートに出す。ミュータントは、その場所を実行するテストだけで試す（`[tests]`）
- **前回の結果を再利用する**。行が変わっていないミュータントは、前回のレポートの結果を使う（`--baseline`）
- **等価ミュータントを自動で見分ける**。生き残ったミュータントを最適化付きでコンパイルし、オブジェクトコードが変更前と同じなら Ignored にする（`equivalence_build`）
- サンドボックスを複数作って並列実行、タイムアウトしたテストはプロセスグループ（Windows はジョブオブジェクト）ごと終了
- `test_memory_limit_mb` でテストの各プロセスのメモリを制限できます（POSIX は `RLIMIT_AS`、Windows はジョブオブジェクト。macOS は `RLIMIT_AS` を受け付けないので、AdaMutant がテストのプロセスの物理メモリ（phys_footprint）を 10 ミリ秒ごとに調べます）。ループ回数などを変えたミュータントが数 GB を確保すると、並列実行中にマシン全体がメモリ不足になり、ラン全体が落ちることがあります。上限を超えた確保は失敗し（Ada では `Storage_Error`）、そのミュータントは Killed になります。macOS では上限を超えた時点でテストのプロセスをまとめて終了し、同じく Killed になります（ログに `adamutant: killed, a process exceeded test_memory_limit_mb` と残ります）。変更前のテストも同じ上限で実行するので、上限が小さすぎればその時点でエラーになります
- レポート: コンソール表、単体で開ける HTML、[mutation-testing-report-schema](https://github.com/stryker-mutator/mutation-testing-elements) v2 の JSON（Stryker のダッシュボードでも読めます）

## 想定している使い方

AdaMutant は、テストと GNATprove の証明を両方使う前提のツールです。次の流れで使うことを想定しています。

1. テストと証明の両方を設定して回します。ミュータントはまずテストにかけ、テストが検出できなかったものだけを証明にかけます（テスト先行）。テストだけ、証明だけで回す設定はありません。
2. 証明だけが検出したミュータントは、「テストの穴の候補」として一覧で見ます。コンソールの `Detected only by the proof (candidates for a missing test):` に、GNATprove が失敗と一緒に出したものによって 3 つに分けて出ます。分けるには GNATprove の反例が要るので、prove のコマンドに `--counterexamples=on` を付けます。

   | 区分 | 判定の材料 | 人がすること |
   |---|---|---|
   | `Confirmed`（確定） | severity が high、またはエラー。high は、GNATprove が反例を本物のコードで実行して、検査が落ちたことを表します | テストで観測できる振る舞いなら、テストを足す |
   | `A contract says too little`（契約が足りない） | GNATprove が `possible fix: add or complete related loop invariants or postconditions` と添えたもの。呼び出し先を契約に（ループをループ不変条件に）置き換えたときだけ、反例で検査が落ちています | どの契約（呼び出し先の事後条件、ループ不変条件）が緩いかを探し、強める |
   | `Undecided`（不明） | それ以外。反例がないもの、反例を本物のコードで確かめられなかったもの（呼び出し先が SPARK でない、ループが長すぎる、など） | 人が判断する。反例があれば一覧に出る |

   - 到達しない分岐のように、テストでは観測できないものは、証明に任せてそのままにします。除外の指定は要りません。
   - 「契約が足りない」に入るのは、本当は動作が変わらない（同値な）ミュータントのことも、本物のバグのこともあります。GNATprove が確かめるのは、自分が選んだ反例 1 つだけだからです。契約を強めると、同値なものは証明が通り、本物のバグは「確定」に移ります。
3. テストも証明も検出できなかったミュータント（Survived）は、テストを足すか、契約を強めます。等価ミュータント（オブジェクトコードが変更前と同じになるもの）は、`equivalence_build` を設定すると自動で見分けて外します（Ignored）。それ以外は Survived のまま残します。
4. 証明が時間切れになったミュータントは、検出扱いにしません。Survived として数え、一覧に `(the proof timed out)` と出ます。2 か 3 として扱い直します。時間切れのミュータントがあると、一覧の下に、その数と対処の案内が出ます。ミュータントで失敗する目標では、証明器が時間の上限まで粘ることがよくあります。証明器にステップ数の上限（`--steps`）を付けると、そうした証明もたいてい、ミュータントの証明の制限時間内に終わります（[ミュータントの証明を速くする](#ミュータントの証明を速くする)）。

[examples/spark_counter](examples/spark_counter) では、次のように出ます（一部）。テストは `Counters.Increment` しか呼ばないので、ほかのミュータントは証明だけが検出します。

```
Detected only by the proof (candidates for a missing test):
  Confirmed: the failure happens with the real code (or GNATprove reports an error)
  #8 src/counters.adb:13:19 ArithmeticOperator (range check, postcondition; no test executes this code)
    - +
    + -
    e.g. when A = 0 and B = 1
  A contract says too little: the failure happens only with the contracts of the calls (or the loop invariants) in place of the code
  #12 src/halves.adb:13:10 ConditionalExpression (range check; no test executes this code)
    - H > 50
    + False
    e.g. when H = 51
  #18 src/halves.adb:16:18 NumericLiteral (range check; no test executes this code)
    - 2
    + 3
    e.g. when H = 34

Survived mutants:
  #6 src/counters.adb:10:16 EqualityOperator
    - >
    + >=
  #10 src/halves.adb:5:18 NumericLiteral
    - 2
    + 3
```

- #8 は `Saturating_Add` の `A + B` を `A - B` にする変異です。A = 0、B = 1 のとき `A - B` が `Count` の範囲を外れ、本物のコードで範囲検査が落ちます。テストを足す候補です（2）。
- `Halves.Half` の本体は `X / 2` を返しますが、契約は「結果は X 以下」としか言っていません。#12 は `H > 50` の判定を消す変異で、実際には H が 50 を超えないので、動作は変わりません（同値）。#18 は `H * 2` を `H * 3` にする変異で、X が 68 以上のとき結果が範囲を外れて Constraint_Error になる、本物のバグです。どちらも GNATprove は、`Half` をその契約に置き換えたときにしか失敗を見つけられず、本物のコードでは確かめられませんでした。`Half` の事後条件を `Half'Result = X / 2` に強めると、#12 は証明が通り、#18 は確定に移ります。
- 生き残った #6 は、`A + B = Max` のときにどちらの分岐も `Max` を返す等価ミュータントです。`equivalence_build` を設定しても（この例では設定していません）、最適化したオブジェクトコードが変わるので自動では外れず、Survived のまま残ります（3）。#10 は `X / 2` を `X / 3` にする変異で、`Half` の契約が緩いので、証明でも検出できません。これも契約を強める箇所を示しています（3）。

## 必要なもの

- GNAT（Ada 2022 対応）と GPRbuild（GNAT 16.1 と GPRbuild 26 で確認。GNAT 14 でもビルドできます）
- 証明に GNATprove（GNATprove 16.1 で確認）。`prove` のコマンドは必須です。GNATprove は SPARK のコード（`SPARK_Mode`）しか解析しないので、それ以外のコードのミュータントを証明が検出することはありません。SPARK のコードが 1 つもないと、GNATprove 16 は失敗で終わります。そのようなプロジェクトでは `prove = "exit 0"`（必ず通るコマンドで、GNATprove は要りません）と書きます（[examples/calculator](examples/calculator) がこの例です）
- E2E テストを動かす場合は Python 3

## ビルド

```sh
make build        # bin/adamutant ができる
make test         # 単体テスト + examples を使った E2E テスト
```

[Alire](https://alire.ada.dev) を使う場合は、`alr build` で同じ `bin/adamutant` ができ、コンパイラも Alire が用意します。Alire でのビルドは警告では止まりません（`ADAMUTANT_WARNINGS_AS_ERRORS=false`）。`make build` は警告で止まります。

## 使い方

プロジェクトのルートで設定ファイルを作って実行します。

```sh
adamutant init                 # adamutant.toml のひな形を作る
adamutant list                 # 作られるミュータントの一覧（実行はしない）
adamutant run                  # 実行してレポートを出す
adamutant run --mutate 'src/parser*.adb' --concurrency 4
adamutant run --since origin/main   # PR で変更した行だけ
adamutant run --baseline .adamutant/reports/mutation-report.json   # 前回の結果を再利用
```

| オプション | 意味 |
|---|---|
| `--config FILE` | 設定ファイル（既定 `adamutant.toml`）。プロジェクトルートは設定ファイルのあるディレクトリ |
| `--mutate GLOB` | 対象ファイルをさらに絞る（複数指定可） |
| `--concurrency N` | 並列サンドボックス数 |
| `--since REF` | git のリビジョン REF と HEAD のマージベースから変更された行だけを変異させる（下記） |
| `--baseline FILE` | 以前の実行の JSON レポート FILE から、行が変わっていないミュータントの結果を再利用する（下記） |
| `--keep-sandbox` | 終了後も `.adamutant/sandbox` を残す（調査用） |

`--since` は Stryker.NET の `--since` と同じく PR の CI 向けです。`git merge-base REF HEAD` からの差分（コミット済み・未コミットの両方）と、無視されていない未追跡ファイルを対象にします。変更のないファイルは読み込まず、変更のあるファイルでも変更行にかからないミュータントは `Ignored`（理由 `unchanged since REF`）になるので、スコアは変更行のミュータントだけで計算されます。仕様（`.ads`）だけを変えた場合でも本体のミュータントは対象になりません。CI では履歴が必要なので、GitHub Actions なら `actions/checkout` に `fetch-depth: 0` を指定してください。

終了コード: 0 = 成功、1 = エラー（設定ミス、元のプロジェクトのビルド・テスト失敗など）、2 = スコアが `break` しきい値未満。

### 設定 (adamutant.toml)

```toml
mutate = ["src/**/*.adb", "src/**/*.ads"]   # 変異させるファイル
exclude = ["src/generated/**"]
build = "gprbuild -p -q -P tests.gpr"       # 必須。失敗したミュータントは CompileError
test = "bin/run_tests"                      # 必須（または [tests]）。終了コード 0 以外なら Killed
prove = 'gnatprove -P prove.gpr --level=1 --steps=2000 --checks-as-errors=on --counterexamples=on "--memcached-server=file:$ADAMUTANT_PROVE_CACHE"'  # 必須。テストが通ったミュータントだけに実行。0 以外なら Killed (証明)
equivalence_build = "gprbuild -p -q -c -P tests.gpr -cargs -O2 -g0"  # 省略可。等価ミュータントの判定に使うビルド
concurrency = 4                             # 既定は CPU 数の半分
timeout_factor = 1.5                        # テスト時間の上限 = 元の時間 * factor + timeout_ms
timeout_ms = 5000
prove_timeout_ms = 0                        # ミュータントの証明 1 回の制限時間（ミリ秒）。既定 0 は、変更前の証明の時間から決める
test_memory_limit_mb = 2048                 # テスト 1 プロセスあたりのメモリ上限。既定 0 は無制限
coverage_analysis = true                    # false で、テストが実行しないコードのミュータントも実行する
bail = true                                 # false で、ミュータントを検出したあとも残りのテストを実行する（[tests] 用）
mutators = ["ArithmeticOperator", "EqualityOperator"]  # 省略時は LoopDirection 以外のすべて
exclude_mutators = ["StringLiteral"]        # 上の一覧から外す（include_mutators にあっても外す）
include_mutators = ["LoopDirection"]        # 上の一覧に足す
mutate_contracts = false                    # true で Pre/Post などのアスペクトも変異
sandbox_exclude = [".git", "obj", "bin"]    # サンドボックスにコピーしないもの
report_dir = ".adamutant/reports"

[thresholds]
high = 80
low = 60
break = 0

# test の代わりに、名前付きのテストコマンドを複数書ける（下記）
# [tests]
# parser = "bin/test_parser"
# lexer = "bin/test_lexer"
```

「元の時間」は、変異させていないプロジェクトのテスト（証明）を全サンドボックスで同時に流したときの最も遅い実行時間です。ミュータントを並列で流すときと同じ負荷で測るので、並列にすると遅くなるテストでも誤って Timeout になりません。

`build`、テスト（`test` か `[tests]`）、`prove` は必須です。ミュータントはまずテストにかけ、テストが通ったものだけを証明にかけます。コマンドは POSIX では `/bin/sh -c`、Windows では `cmd.exe /c` で実行され、環境変数 `ADAMUTANT_MUTANT_ID` が渡されます。ミュータントのビルド・テスト・証明には、変異させたファイルのパス（`files` に書いたとおりのプロジェクトルートからの相対パス）が `ADAMUTANT_MUTANT_FILE` で、変異させた行が `ADAMUTANT_MUTANT_LINE` で渡されます（ベースラインの実行では空です）。証明のコマンドには、証明結果のキャッシュのディレクトリが `ADAMUTANT_PROVE_CACHE` で渡されます（[ミュータントの証明を速くする](#ミュータントの証明を速くする)）。cmd.exe は `bin/test` の `/` 以降をスイッチとして解釈するため、`/` を含むパスは `test = '"bin/test"'` のように引用符で囲んでください（`/bin/sh` でもそのまま動きます）。未知のキーはエラーになります。

### 前回の結果の再利用

`--baseline FILE` に以前の実行の JSON レポート（`mutation-report.json`）を渡すと、行が変わっていないミュータントは、そのレポートの結果を使います。再利用したミュータントは実行しません。`statusReason` の末尾に `(from the baseline report)` が付きます。

どのミュータントを同じとみなすかは、ソースを行単位で比べて決めます。レポートに入っているソースと今のソースを比べ、ミュータントのある行がすべて変わっておらず、桁、ミューテーターの種類、置き換え後の文字列が同じなら、同じミュータントです。上に行を足して行番号がずれても対応が取れます。git は使いません。

行の対応は、両方のソースに 1 回ずつしか出てこない行を手がかりにして決めます。`begin` や `end if;` のように何度も出てくる行は、手がかりの行と続いている場合だけ対応させます。そのため、同じ文面の別の行と取り違えることはありません。2 つの関数の順番を入れ替えた場合は、片方だけを「変わった行」として扱います。

再利用する結果は、`--since` を付けるかどうかで変わります。

| 使い方 | 再利用する結果 | 実行するミュータント |
|---|---|---|
| `--baseline FILE` | レポートのソースから変わっていない行の Killed、Timeout、CompileError | レポートのソースから変わった行のミュータントと、前回検出できなかったミュータント（Survived など） |
| `--since REF --baseline FILE` | REF から変わっていない行は、レポートにあるすべての結果（Survived、等価ミュータントの Ignored を含む）。REF から変わった行は、上の行と同じ | REF から変わった行のミュータント（レポートのソースから変わっていない行で、すでに検出済みのものを除く） |

- `--baseline` だけのときは、テストを足したあとの再実行に向いています。前回検出できたミュータントは飛ばし、生き残っていたミュータントだけを試し直します
- `--since` と組み合わせると、PR の CI で、変更した行だけを実行しつつ、全体のスコアとレポートを出せます。このとき、変更のないファイルも読み込みます。FILE には、たとえばメインブランチで全体を実行したときのレポートを使います
- `--since` と組み合わせたとき、REF から変わっていない行のミュータントで、レポートに使える結果がないものは、`--since` だけのときと同じく Ignored（`unchanged since REF`）のままで、スコアに入りません
- FILE がないときは、警告を出し、結果を再利用せずに実行します（最初の実行のため）。FILE が JSON でないとき、`files` を持たないとき、ファイルでないときはエラーです
- ビルドが時間切れになった CompileError は再利用しません（`--since` を付けていないときは、もう一度実行します）
- レポートを書き出す前に FILE を読むので、FILE に今回の出力先と同じファイルを指定できます

再利用した結果は、行が変わっていないことだけを根拠にしています。次の場合は古い結果が残るので、ときどき `--baseline` なしで全体を実行してください。

- テストを削った、または弱くした（検出済みのはずのミュータントが、今は生き残る）
- 変わっていない行の動作が、ほかの行やほかのファイルの変更で変わった
- ビルドやテストのコマンド、コンパイラを変えた
- 変異の種類の設定を変えた（`mutators`、`exclude_mutators`、`include_mutators`、`mutate_contracts`）。`--since` があると、変わっていない行の新しいミュータントは、レポートに結果がないので Ignored（`unchanged since REF`）のままです
- マシンの負荷で結果が変わるミュータント（時間切れで Timeout になったもの）

### ミュータントの証明を速くする

証明のコマンドは、ミュータントごとにユニット全体（またはコマンドが指定する範囲）を証明します。大きなユニットでは、ミュータントが変えていない目標の証明に、毎回時間がかかります。

GNATprove には、証明結果のキャッシュがあります（`--memcached-server=file:<ディレクトリ>`）。AdaMutant は、証明のコマンドに、キャッシュのディレクトリを `ADAMUTANT_PROVE_CACHE` で渡します。これを、証明器のステップ数の上限（`--steps`、下記）と一緒に、コマンドに足してください。

```toml
prove = 'gnatprove -P prove.gpr --level=1 --steps=2000 --checks-as-errors=on --counterexamples=on "--memcached-server=file:$ADAMUTANT_PROVE_CACHE"'
```

Windows（cmd.exe）では `%ADAMUTANT_PROVE_CACHE%` と書きます。

- キャッシュは、変更前のプロジェクトの証明で埋まります。ミュータントの証明では、変わっていない目標の答えがキャッシュから返り、証明し直すのは、ミュータントで変わった目標だけです
- キャッシュのキーは目標そのものなので、目標は、同じ目標に証明器が前に出した答えを受け取ります。結果は、キャッシュなしの全体の証明と同じです。GNATprove 16.1 で、反例や `possible fix` を含むメッセージが同じになることを確かめました（反例は、キャッシュから答えが返った目標でも、本物のコードで確かめ直します）。どの手続きの証明に影響するかを、AdaMutant が推測することはありません
- 証明器には、ステップ数の上限（`--steps`。変更前のプロジェクトを証明できる値）を付けてください。GNATprove 16.1 は、キャッシュを使うと、ステップ数ではなく時間の上限で止まる証明器を、上限のおよそ 4 倍の時間動かします。試したときは、`--timeout=2` の CVC5 が、証明できない目標 1 つにつき 8 秒動きました。ミュータントで失敗する目標がキャッシュなしよりずっと遅くなり、ミュータントの証明の制限時間（何も失敗しない、変更前のプロジェクトの証明の時間から決めます）に収まらないと、そのミュータントは Survived になります。ステップ数の上限があれば、証明器の時間は、キャッシュのあるなしで同じでした。ステップ数なら、結果がマシンの負荷にも左右されません。

  ステップ数の上限は、キャッシュを使わないときにも役に立ちます。ミュータントで失敗する目標では、証明器が上限まで粘ります。時間の上限だけだと、ミュータントの証明の制限時間に収まらないことがあります（`--level=2` で試したとき、`--steps=5000` なら検出した 3 つのミュータントが、キャッシュのあるなしにかかわらず Survived でした）。値は、変更前のプロジェクトに必要なステップ数に余裕を持たせて決めてください（`--report=statistics` で、チェックごとのステップ数が分かります）。少なすぎると、変更前のプロジェクトの証明が失敗し、AdaMutant はそこで止まります
- 目標には行番号が入っています。AdaMutant は、置き換えた部分にあった改行を置き換えのあとに残すので（複数行の文を削除したときなど）、後ろの行はずれず、その目標もキャッシュに当たります
- キャッシュはサンドボックスごとに別のディレクトリで（`.adamutant/sandbox/prove-cache/<番号>`）、実行のたびに空から始まり、サンドボックスと一緒に消えます。時間内に終わらなかった証明が書いた項目は、消します（途中で止めたために壊れた項目は、GNATprove を止めてしまうため）
- 速くならないのは、ミュータントで新しく失敗する目標と、ミュータントが多くの目標を変えるとき（多くの場所で使う定数を変えたときなど）です。`prove_timeout_ms` を決めるときは、キャッシュなしの全体の証明が終わる時間を残してください

GNATprove 16.1 での例です。24 個の関数（チェック 480 個）からなるユニットで、1 つの関数の本体を変異させました。全体の証明はキャッシュなしで 40.9 秒、変更前の証明で埋めたキャッシュありで 1.4 秒でした。失敗したチェックは、どちらも同じ 2 つです。

`prove_timeout_ms` は、ミュータントの証明 1 回の制限時間です。0（既定）のときは、テストと同じく、変更前のプロジェクトの証明の時間から決めます。時間内に終わらなかったミュータントは、検出扱いにしません（Survived）。

## ミュータント

| 名前 | 例 |
|---|---|
| ArithmeticOperator | `+`↔`-`, `*`↔`/`, `mod`,`rem`→`*`（`mod`↔`rem` は符号が異なるときしか差が出ず、ほぼ等価ミュータントになるため）, `**`→`*`, `&` は対象外 |
| EqualityOperator | `<`→`<=`,`>=`、`=`↔`/=` など |
| LogicalOperator | `and`↔`or`, `and then`↔`or else`, `xor`→`or`。`A and then B and then C` のような連鎖では `(A or else B) and then C` のように括弧を補う |
| UnaryOperator | `not X`→`X`, `-X`↔`+X`, `abs X`→`X` |
| BooleanLiteral | `True`↔`False` |
| MembershipOperator | `in`↔`not in` |
| ConditionalExpression | `if`/`elsif` の条件 → `True`/`False`、`while` → `False`、`exit when` → `True` |
| StatementDeletion | 代入文、手続き呼び出し文、raise 文、値のない return 文（`return;`）→ `null;`。`exception` や `end`（`end if`、`end loop`、`end case`、`end select` を除く）のすぐ前にある `return;` は、本体の最後なら消しても動きが変わらないので除きます（入れ子のブロックの最後では動きが変わりますが、これも除かれます）。`else` のない `if`・`elsif` の分岐が raise 文や `return;` だけのときも除きます。消したプログラムは、ConditionalExpression の「条件 → `False`」と同じだからです。exit 文と delay 文は変異させません。exit 文を消すとループが終わらなくなることがあり、delay 文の待ち時間はテストでも証明でもほとんど確かめないからです |
| NumericLiteral | `0`→`1`, `1`→`0`, `n`→`n+1`, 実数 → `0.0`。基数付き・指数付きの整数リテラルも同じ規則で、基数は保ちます（`16#FF#`→`16#100#`, `1E6`→`1000001`）。宣言した部分型の範囲の上下限 `String (1 .. 6)` などは対象外 |
| StringLiteral | `"abc"`→`""`, `""`→`"AdaMutant was here!"` |
| AttributeSwap | `'First`↔`'Last`、`'Min`↔`'Max`、`'Succ`↔`'Pred`、`'Floor`↔`'Ceiling`、`'First_Valid`↔`'Last_Valid`。入れ替え先も同じ型の値を返すので、型は合います。それでも、選択肢が重なってはいけない所や型を覆わなければならない所（case の選択肢、名前付きの配列集成体）や、静的な値が範囲を外れる所（`Color'Succ (Color'Last)`）ではコンパイルが通らず、CompileError になります。宣言の部分型の中（`X : String (1 .. A'Last)`、`subtype S is T range T'First .. T'Last`）は、NumericLiteral の範囲の上下限と同じく変異させません。初期値（`L : constant Natural := A'Last`）と宣言のアスペクト（述語。`mutate_contracts` のとき）は変異させます |
| LoopDirection | `for I in A .. B loop`↔`for I in reverse A .. B loop`。`reverse` を足すのは、範囲（`A .. B`、`X'Range`）を回すループと、そのファイルか仕様か Standard で宣言された型・部分型の名前だけを回すループ（`for I in Index loop`、`for C in Character loop`）です。ほかの名前（`for C in L loop`、`for I in Types.Index loop`）やイテレータ（`for C in V.Iterate`、`for E of A`）のループは、逆向きに回せないコンテナやイテレータかもしれないので、足しません。量化式・集成体の中の `for` も変異させません。反復のフィルタの `when` から後ろは、範囲として見ません。`reverse` を外すのは、イテレータも含めてすべての `for ... in reverse` のループです（前向きなら必ずコンパイルが通ります）。**既定では使いません**。回す順序が結果に影響しないループ（合計、別の配列へのコピーなど）は多く、そのミュータントは等価です。それでもループ不変条件があると証明はたいてい失敗するため、「テストの穴の候補」に挙がってしまいます。使うときは `include_mutators = ["LoopDirection"]` と書きます |

`with`/`use` 節、`pragma`、表現節（`for X'Size use ...`）、`digits`/`delta` は変異させません。サブプログラムの仮引数の既定値も、宣言と本体で一致していないとコンパイルできない（完全準拠）ため変異させません（`is null`、`is abstract`、式関数、ジェネリック仮サブプログラムの既定値は変異させます）。アスペクト（`Pre`, `Post`, `Type_Invariant` など）とゴーストコード（`Ghost` アスペクト付きで宣言されたサブプログラム・オブジェクト・型の宣言と本体、およびそれらを呼び出す・代入する文）は `mutate_contracts = true` のときだけ変異させます。ゴーストの名前は変異対象の `.adb` と、同じ名前の `.ads` から集めます。

ミュータントを無効にするコメントはありません。テストで観測できないミュータントは証明に任せ（[想定している使い方](#想定している使い方)）、等価ミュータントは `equivalence_build` で見分けます。

## 状態とスコア

| 状態 | 意味 |
|---|---|
| Killed | テストまたは証明が失敗した（検出できた） |
| Timeout | テストが時間内に終わらなかった（検出扱い） |
| Survived | テストも証明も通った、または証明が時間内に終わらなかった（検出できなかった） |
| NoCoverage | 今の版では使わない。どのテストも実行しないミュータントも証明にかける（未検出扱い） |
| CompileError | ミュータントがビルドできなかった（スコア対象外） |
| RuntimeError | コマンドを起動できなかったなど（スコア対象外） |
| Ignored | 等価ミュータントと判定した、または `--since` のリビジョンから変わっていない行にある（スコア対象外） |

`スコア = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage) * 100`

### テストごとの結果

`test` の代わりに `[tests]` の表を書くと、テストコマンドに名前を付けて複数指定できます。キーが名前、値がコマンドです。名前に使えるのは英数字と `_`、`-`、`.` です。設定のキーと同じ名前（`build`、`test`、`prove` など）と、レポートが証明を表すのに使う `proof` は使えず、大文字と小文字だけが違う名前を 2 つ使うこともできません。`[tests]` は設定のあとに書きます。`test` と `[tests]` を両方書くことはできません。

```toml
[tests]
parser = "bin/test_parser"
lexer = "bin/test_lexer"
```

- テストは書いた順に実行します。変更前のプロジェクトでは、すべてのテストが通る必要があります。タイムアウトの時間はテストごとに測ります
- ミュータントは、その場所を実行するテストだけで試します（`coverage_analysis = true` のとき）。どのテストがその場所を実行するかは、JSON の `coveredBy` に出ます
- ミュータントを検出したテスト（失敗した、または時間内に終わらなかったテスト）の名前が `killedBy` に出ます。`testsCompleted` は、そのミュータントで実行したテストの数です。テストの一覧は `testFiles` に出ます
- 既定では、最初にミュータントを検出したテストで、そのミュータントの実行を終えます。`bail = false` にすると、その場所を実行するテストをすべて実行します。時間はかかりますが、ミュータントを 1 つも検出しないテストが分かります。無限ループになるミュータントは、その場所を実行するテストの数だけタイムアウトを待ちます
- テストごとのログは `mutant-<番号>-test-<名前>.log` です
- まとめたビルドに入らないミュータント（宣言の中のものなど）は、どのテストが実行するか分からないので、すべてのテストで試します

テストを選んで実行するので、次の 2 つが必要です。満たせないときは `coverage_analysis = false` にしてください（すべてのミュータントをすべてのテストで試します）。

- どのテストも、ビルドしたテストプログラムを実行すること。実行した場所を 1 つも記録しなかったテストがあると（プログラムを実行しないテスト、記録先に書けない環境で動くテストなど）、そのテストが何を実行するか分かりません。AdaMutant は警告を出し、その実行ではテストを選ばず、すべてのミュータントをすべてのテストで試します。記録の有無はテスト単位で見ます。1 つのテストが複数のプログラムを実行し、その一部だけが記録できない場合は見分けられません
- テストが互いに依存しないこと。あるテストが書いたファイルを別のテストが読む場合、前のテストを飛ばすと、後のテストは古いファイルを読みます

コンソールには、テストごとに、そのテストが場所を実行するミュータントの数（Covers）と、検出したミュータントの数（Kills）が出ます。実行する場所を調べていないときは、Covers は `-` です。

```
Test  | Covers | Kills
----------------------
arith |      5 |     4
misc  |     30 |    24
idle  |      1 |     0
Tests that detect no mutant: idle
```

Covers が多いのに Kills が少ないテストは、コードを実行するだけで結果を確かめていない可能性があります。`bail = true` のときの Kills は、最初に検出したテストだけを数えた値です。

### 証明のどの検査で検出したか

証明で検出したミュータント（Killed、`killedBy` が証明）には、GNATprove が証明できなかった検査の種類を記録します。JSON の `killedBy` は `["proof: postcondition", "proof: range check"]` のようになり、`statusReason` には GNATprove の最初のメッセージが入ります。コンソールには、検査の種類ごとの数が出ます。

```
Mutants killed by the proof, by the check that fails (alone: no other kind of check fails for the mutant):
  range check   |     5 |     2 alone
  postcondition |     5 |     2 alone
```

`alone` は、その種類の検査だけで検出したミュータントの数です。範囲検査やオーバーフロー検査だけで検出したミュータントは、契約を見直すきっかけにはなりますが、それだけで契約が弱いとは言えません。GNATprove は、検査のあとのコードを「その検査は成り立つ」という前提で証明します。そのため、ミュータントが誤った動作をする入力は、実行時検査で止まり、事後条件の証明には届かないことがあります。上の例の `range check` だけで検出した 2 つも、事後条件が結果を完全に決めている関数のミュータントです。

- 種類の名前は GNATprove のメッセージから取ります（`... might fail` の前の部分）。メッセージが引用している名前（変数や手続きの名前）は種類に含めません。初期化されていないオブジェクトについてのフロー解析のメッセージは、まとめて `initialization` です
- 変更前のプロジェクトの証明にも出ているメッセージは数えません（同じファイルの同じ文面のメッセージを、行と桁が違っても同じものとみなします）
- メッセージを読み取れなかったときは、これまでどおり `killedBy` は `["proof"]` です
- GNATprove 16 は、メッセージの場所を次の行（`--> file:line:col`）に出します。AdaMutant は、この形式も、それより前の版の 1 行の形式も読みます
- 証明だけが検出したミュータントは、コンソールの `Detected only by the proof (candidates for a missing test):` にも 1 つずつ出ます。括弧の中は証明できなかった検査の種類です。どのテストも実行しない場所のミュータントには `no test executes this code` が付きます。GNATprove が反例を出したときは、その下の行に出ます
- 3 つの区分（[想定している使い方](#想定している使い方)）は、`statusReason` の書き出しでも分かります。`proof failed, confirmed: ` が確定、`proof failed, a contract says too little: ` が契約が足りないもの、それ以外の `proof failed` が不明です。反例は、メッセージのあとの括弧に入ります（`... (e.g. when H = 51)`）。`--baseline` で結果を再利用するときも、ここから区分を読み取ります（書き出しのない以前の版の理由は、メッセージが high かエラーなら確定とします）
- 区分の材料は、変更前のプロジェクトの証明にないメッセージから、high かエラーのもの（確定）、`possible fix: add or complete related loop invariants or postconditions` が付いたもの（契約が足りない）の順に選びます。GNATprove は、`--counterexamples=on` のときに反例を出し、`--check-counterexamples=off` でなければ、それを本物のコードで確かめます。反例がないと、ほとんどが不明になります。証明が反例を 1 つも出さなかったときは、コンソールにその旨が出ます。失敗が複数あるミュータントは、そのうち 1 つが入る区分のうち、いちばん上のものに入ります。たとえば、`possible fix` の付いた失敗と付いていない失敗があれば「契約が足りない」です。契約を強めても残る失敗は、そのあと「確定」か「不明」に出ます
- 読むのは GNATprove の既定の出力（`--output=pretty`）です。`--output=oneline` でも、メッセージの中の反例と `possible fix` を読みます。`--output=brief` には反例が出ません
- 証明が時間内に終わらなかったミュータントは Survived です（`statusReason` は `... the proof did not finish within the timeout`）。証明が失敗するはずなのか、遅いだけなのかを区別できないためです。`--baseline` では、以前の版のレポートにある証明の Timeout は実行し直します。`--since` のリビジョンから変わっていない行では、Survived として再利用します
- 以前の版は、テストだけ、証明だけでも回せました。`--baseline` では、今の版なら出さない結果は再利用しません。NoCoverage、テストだけまたは証明だけで生き残ったもの、テストをせずに証明が検出したものです。そのミュータントは実行し直します。ただし、`--since` のリビジョンから変わっていない行では、`--since` だけのときと同じく Ignored（`unchanged since REF`）のままです

## 仕組み

1. 元のプロジェクトを `.adamutant/sandbox/1` にコピーし、ビルド、テスト、証明を一度通して所要時間を測る。失敗したらエラーで止まる
2. 同じ状態をワーカー数ぶんのサンドボックスに複製
3. **ミュータントをまとめたソース**を作って 1 回ビルドし、ミュータントごとにテストだけを実行する（下記）。その前に、どのミュータントも有効にせずにテストを実行し、テストが実行した場所を記録する。実行しなかった場所のミュータントは、テストを実行せず証明に回す（下記）
4. まとめられなかったミュータントは、各ワーカーが 1 ファイルだけを書き換え → `build` → `test` → 元に戻す、を繰り返す。GNAT の ALI のタイムスタンプは 1 秒単位で、Windows では偶数秒に切り上げられるため、書き換えるたびに mtime を 2 秒以上進めて再コンパイル漏れを防いでいる
5. テストで検出できなかったミュータントを 1 つずつ証明にかける（1 ファイルを書き換え → `prove` → 元に戻す）。証明は、まとめたソースでは行わない。どのミュータントが原因かを切り分けられないため
6. `equivalence_build` があるとき、生き残ったミュータントを 1 つずつそのコマンドでビルドし、オブジェクトファイルが変更前と同じなら等価ミュータントとして Ignored にする（下記）
7. ログは `.adamutant/logs`、レポートは `report_dir` に出力

変更前のプロジェクトのビルドとテストのあとでサンドボックスにライブラリ（`.a`、`.lib`、`.so`、`.so.<バージョン>`、`.dll`、`.dylib`）があるときは、手順 3 と 4 のどのビルドも、いちばん新しいライブラリが書かれてから 2 秒以上たって始めます。gprbuild は、ライブラリのタイムスタンプがオブジェクトより古くなければライブラリを作り直しません。そのため、同じ秒のうちにコンパイルしたミュータントはライブラリに入らず、テストは前のビルドのコードを実行してしまいます。どのビルドも書き直さないライブラリでは待ちません。AdaMutant が見るのはサンドボックスの中のライブラリだけです。プロジェクトの外のディレクトリにライブラリを書くビルドは対象外で、そのようなディレクトリはすべてのサンドボックスが共有することにもなります。待ち時間は、ファイルのタイムスタンプとこのマシンの時計を比べて決めます。そのため、ネットワークファイルシステムでは、ファイルサーバーの時計が 2 秒以上遅れていてはいけません。

### ミュータントをまとめたビルド

ミュータントの入ったソースは、たとえば次のようになります（`ADAMUTANT_ACTIVE_1` は、テスト実行時の環境変数 `ADAMUTANT_MUTANT_ID` の値を返す関数です。0 のときはどのミュータントも有効になりません。引数は場所の番号で、その場所にある最初のミュータントの番号です）。

```ada
case ADAMUTANT_ACTIVE_1 (17) is
when 17 =>
X := X - 1;
when 18 =>
X := X + 0;
when others =>
X := X + 1;
end case;
```

まとめるのは、字句解析だけで範囲を確実に決められる次の場所のミュータントです。

| 場所 | 書き換え |
|---|---|
| 単純な文（代入、手続き呼び出し、`return`、`exit`、`raise` など） | `case` 文 |
| `if`、`elsif`、`while` の条件 | `case` 式 |
| 式関数の式 | `case` 式 |

次のものはまとめず、これまでどおり 1 つずつビルドします。

- 宣言の中のミュータント（定数、名前付き数、型の範囲など）、`for` の範囲、`case` の選択肢、アスペクト。静的な式が必要なことがあり、実行時の切り替えにできないため
- StatementDeletion。削除した文が変数への最初の代入だった場合、ミュータントではその変数が未初期化になる。最適化するコンパイラは、未初期化の変数に「もう一方の分岐で代入される値」を割り当ててよいので、まとめたビルドではミュータントが元のプログラムと同じ動きになり、検出できたはずのものを見逃す。ただし、その文が実行されたかどうかは、まとめたビルドで記録する（下記）
- タスク、プロテクト型、`accept`、`select` を含むファイル、名前付きの文、拡張 return のオブジェクト宣言

まとめたビルドでコンパイルエラーが出たときは、エラーの行がどのミュータントの行かを調べ、そのミュータントを CompileError にして、残りでビルドし直します。どのミュータントの行でもない場所でビルドが失敗したときは、エラーで終了します。

必要なもの。

- テストプログラムのメインサブプログラムが Ada で、ビルドが GNAT の ALI ファイルを残すこと。有効なミュータントの番号を返す関数は、AdaMutant が生成するユニット `AdaMutant_Schemata_Support` にあり、サンドボックスの中でだけ、メインのソースと同じディレクトリに置いてメインに `with` を足します。メインが見つからないときは警告を出し、すべてのミュータントを 1 つずつビルドします
- C の `getenv` が使えること（環境変数を読むため）。実行した場所の記録には `getpid`、`fopen`、`fputs`、`fflush` も使います
- 実行した場所の記録先は、絶対パスで生成コードに入ります。テストコマンドがテストプログラムを別のファイルシステムで実行する場合（プロジェクトを別の場所にマウントしたコンテナなど）、そのプロセスは記録できません。一部のプロセスだけが記録できないと、警告は出ません。そのような構成では `coverage_analysis = false` にしてください
- テストコマンドが、ビルドした実行ファイルをそのまま実行すること。`ADAMUTANT_MUTANT_ID` は以前からテストコマンドに渡している環境変数で、テストプログラムまで届く必要があります

### テストが実行しないコード

どのテストも実行しない場所のミュータントは、テストでは検出できません。AdaMutant はそのミュータントのテストを飛ばし、すぐに証明にかけます。証明も通ったときは Survived で、`statusReason` は `no test executes this code, and the proof passed` です。テストを実行しない分、時間が減ります。

仕組みは次のとおりです。まとめたビルドでは、ミュータントの切り替えに使う関数が、呼ばれた場所の番号を記録します。記録するのは、どのミュータントも有効でないとき（`ADAMUTANT_MUTANT_ID` が 0 か未設定のとき）だけです。AdaMutant は、ミュータントを実行する前に、どのミュータントも有効にせずにテストを一度実行します。そのときテストプログラムの各プロセスが、実行した場所の番号を `.adamutant/logs/coverage/<プロセス番号>.txt` に書きます。記録先のディレクトリは、生成したユニットに埋め込んであります。まとめた結果は `.adamutant/logs/coverage.txt` に残ります（`[tests]` を使うときは、テストごとに `coverage-<名前>.txt`）。

- 対象は、まとめたビルドに入るミュータントと StatementDeletion です。StatementDeletion はまとめたビルドには入りませんが、文が実行されたかどうかは記録します。実行されなかった文の StatementDeletion は、ビルドしてから、テストを飛ばして証明にかけます
- 宣言の中のミュータントなど、まとめられないものは対象外で、これまでどおりテストを実行します
- テストプログラムが何も記録しなかったときは、警告を出し、すべてのミュータントを実行します（記録先に書けない場合など）。テストプログラムは、起動した時点で 1 行目を書きます。そのため、どの場所も実行しなかった場合と、記録できなかった場合は区別できます
- 記録のときの実行は、ミュータントを実行するときの実行を含んでいる必要があります。次のような場合は、テストで検出できるはずのミュータントのテストが飛ばされるので、`coverage_analysis = false` にしてください
  - 乱数や時刻で実行する経路が変わるテスト
  - `ADAMUTANT_MUTANT_ID` や `ADAMUTANT_MUTANT_FILE` を見て、実行するテストを変えるテストコマンド（記録のときは、それぞれ 0 と空です）
- コンソールには、どのテストも実行しない行を `Lines that no test executes:` として出します。JSON には、ミュータントごとに `coveredBy` を出します（実行されたら `["tests"]`、されなかったら `[]`、調べていなければ項目なし。`[tests]` を使うときは、その場所を実行するテストの名前）

ミュータントを 1 つずつビルドする場合との違いが 1 つあります。まとめたソースではスタイル検査を切っており、また、ファイル全体を見て出る警告（文を削除したために変数が使われなくなった、など）は出ません。そのため、警告をエラーにしているプロジェクト（`-gnatwe`、`-gnaty`）では、警告だけが理由でコンパイルできなかったミュータントが CompileError ではなく実行されるようになります。

### 等価ミュータントの判定

元のプログラムと動作が同じミュータント（等価ミュータント）は、どんなテストを書いても検出できません。`equivalence_build` にコマンドを書くと、AdaMutant は生き残ったミュータントをそのコマンドでビルドし、できたオブジェクトファイルを変更前のものと比べます。すべて同じなら、そのミュータントは変更前と同じプログラムなので、Ignored（理由は `equivalent mutant: ...`）にしてスコアから外します。等価と判定したミュータントは、コンソールに `Equivalent mutants` として出ます。

```toml
equivalence_build = "gprbuild -p -q -c -P tests.gpr -cargs -O2 -g0"
```

コマンドは、`build` のコマンドから最適化とデバッグ情報のスイッチだけを変えたものにしてください。

- 最適化を付けます（`-O2`）。最適化なしでは、`A > B` と `A >= B` のような違いがそのまま機械語に残り、等価なものも同じになりません
- デバッグ情報を付けません（`-g0`）。デバッグ情報には桁の位置などが入るので、等価なものも同じになりません
- それ以外のスイッチは `build` と同じにします（アサーションの有効・無効、検査の抑止、シナリオ変数など）。判定は、このコマンドのコンパイラとスイッチでできるプログラムについてのものです
- 変異したファイルに依存するユニットを、すべてコンパイルし直すコマンドにします（gprbuild にプロジェクト全体を渡せば、そうなります）。仕様部の定数、ジェネリックの本体、インライン展開される本体のミュータントは、ほかのユニットのオブジェクトにだけ現れます。変異したファイルだけをコンパイルするコマンドは使えません
- コンパイルだけをします（gprbuild なら `-c`）。バインドとリンクは要りません。ライブラリプロジェクトでは、リンクまで行うと等価なミュータントを見逃すことがあります

「同じ」と出たミュータントは等価ですが、「違う」と出たミュータントが等価でないとは限りません。コンパイラが同じコードにまとめられる範囲のものだけが見つかります。

AdaMutant は、誤って等価と判定しないために、次のことをします。

- 変更前のプロジェクトをこのコマンドでビルドする前に、サンドボックスのオブジェクトファイルと ALI ファイルを消します。`build` で作ったオブジェクトが残っていると、gprbuild はスイッチが違っても作り直さないためです（`-s` を付けない場合）。全体を一度コンパイルし直すので、その分の時間がかかります
- 比べるのは、サンドボックスの中の拡張子 `.o` と `.obj` のファイルすべてです。バインダーが作るファイル（`b__*.o`、`b~*.o`）は、ミュータントごとに変わるので比べません
- ファイルごとに、検出済み（Killed）のミュータントを 1 つこのコマンドでビルドし、オブジェクトファイルが変わることを先に確かめます。コマンドがそのファイルをコンパイルしていなければ、オブジェクトファイルは変わらず、すべてが等価に見えてしまうためです。変わらないとき（3 つまで試します）、検出済みのミュータントがないとき、ビルドが失敗するときは、警告を出し、そのファイルの生き残りは調べません
- ミュータントをビルドしたあと、GNAT の ALI ファイルを調べ、変異したファイルに依存するユニットがすべてコンパイルし直されたことを確かめます。そうでないミュータントは等価としません
- ミュータントを 1 つ比べるたびに、オブジェクトファイルを変更前のものに戻します
- 契約（アスペクトとゴーストコード）のミュータントは調べません。アサーションを無効にしたビルドではオブジェクトに現れませんが、契約としては別のものだからです（`mutate_contracts = true` のとき）
- コマンドが変更前のプロジェクトで失敗したときや、途中でファイルの読み書きに失敗したときは、警告を出して判定をやめます。それまでの結果は残ります

## サンプル

- [examples/calculator](examples/calculator): わざと境界値を検査しないテスト。生き残ったミュータント、タイムアウト、どのテストも実行しない行、等価ミュータントの判定が見られる
- [examples/spark_counter](examples/spark_counter): テストが一部の振る舞いしか確かめず、残りを GNATprove の証明が検出する例。証明だけが検出したミュータントの一覧で、確定したものと、契約が足りないもの（`Halves.Half` の緩い事後条件）が見られる

```sh
cd examples/calculator && ../../bin/adamutant run
```
